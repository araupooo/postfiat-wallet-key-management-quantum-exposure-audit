# Fresh-environment reproduction

## Procedure (2026-11-14)

1. Copied the pack to a clean directory:
   `cp -a <pack>/. /tmp/pack-repro-wallet/`
2. Ran the regeneration from scratch in that copy (no files carried
   over except the pack itself):
   `cd /tmp/pack-repro-wallet && bash -c 'bash run_all.sh; echo "run_all.sh exit code: $?"'`
   Exit code: **0**. Output tail: `run_all.sh: OK` followed by
   `run_all.sh exit code: 0`. The full raw console log of that run is
   shipped as `results/run_log.txt` (unedited).
3. Compared the regenerated derived outputs against the shipped ones
   with `cmp` (byte-for-byte) — all **IDENTICAL**:
   - `results/summary.json`
   - `results/summary.txt`
   - `results/transactions.csv`
   - `results/key_exposure.csv`
   - `results/signer_keys.csv`
   - `results/mechanism_counts.csv`
   - `results/fetch_log.json`
   - `results/sample_ledger_data.json`
   - `docs/index.html`
4. Verified the digest manifest in the pack:
   `bash verify_digests.sh --check` — exit code **0**, all files OK.
   The raw output of that check is shipped as
   `results/digest_check_output.txt`.

## Result

**0 failures.** The offline regeneration is deterministic: a fresh copy
of the pack regenerates byte-identical derived outputs from the
vendored sample (no network access, no timestamps written into
outputs — the fetch date is copied from the vendored sample).

## Notes

- Two paths exist, and both are recorded here:
  - **Offline (default, reproduced here):** `bash run_all.sh`
    regenerates everything from the vendored
    `results/sample_ledger_data.json`. No network access. This is the
    path a reviewer reproduces.
  - **Live (authoring only):** `python3 harness.py --live` re-probes
    the public read-only endpoint `https://rpc.testnet.postfiat.org/`
    (no credentials, no secrets), overwrites
    `results/sample_ledger_data.json` and `results/fetch_log.json`,
    and regenerates all derived outputs. A live re-probe produces
    different ledger numbers (validated ledger advances) and may
    produce different transaction counts — that is expected, and is
    why the vendored sample is the reproducible artifact.
- The pinned tree itself is an input to the reproduction, not part of
  the pack: the fresh copy checked the same pinned worktree (detached
  HEAD at `0085a1ff`) and recorded `tree_head_matches_pinned: true`
  in `results/summary.json`. A different tree commit would be recorded
  as a mismatch, not silently accepted. When the pinned tree is
  absent (e.g. `POSTFIATD_TREE=/nonexistent`), the harness records
  `tree_head_commit: ""` and `tree_head_matches_pinned: false` and
  still exits 0 — the tree check never blocks reproduction.
- The live probe was run twice during authoring. The first run
  exposed two harness bugs: transactions in the `ledger` response
  carry their result in `metaData`, not `meta` (so `by_result` came
  out empty), and the manifest `master_key` field was wrongly
  redacted — it is the validator's master *public* key, already
  published by the node, and redacting it broke the
  ephemeral==master comparison between the vendored sample and the
  derived summary. Both were fixed in the harness and the probe was
  re-run from scratch; only the second run's data is vendored.
  The second run: 250/250 ledgers fetched, 0 failures, 0 redactions,
  265/265 requests succeeded on the first attempt.
- `results/run_log.txt` is the raw log of the fresh-environment run
  described above. It is shipped as a record of that run, not
  regenerated by `run_all.sh` (regenerating it would change the file
  being logged). The digest manifest covers it like every other pack
  file.
- `results/digest_check_output.txt` is the raw output of
  `bash verify_digests.sh --check` run in the pack after the run log
  was added. It lists every pack file except itself: a check output
  cannot list the file it is being written into. A reviewer running
  the check themselves will see all files OK, including
  `digest_check_output.txt`.
- The `.sh` files are executable in this pack. A GitHub web upload
  strips the executable bit; run the scripts with `bash` after a web
  upload.
- Environment at reproduction time: Python 3.12.3, git 2.43.0,
  GNU coreutils `sha256sum` (Ubuntu), same machine as authoring.
- The temporary copy at `/tmp/pack-repro-wallet/` is disposable; it was
  left in place for inspection and can be deleted.
